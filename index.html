Solana transaction size calculator — offline, no RPC

Answers SSE Q23875 “Get size of the transaction”: serialize() throws encoding overruns Uint8Array past the ~1232-byte packet limit, so this page counts bytes arithmetically (signatures + header + keys + blockhash + instructions + ALT lookups + compact-u16 length prefixes) without ever allocating the oversized buffer. 100% local — no keys, no RPC, no CDN.

1 · Message shape

Fixed per-tx constants: header 3 B · recent blockhash 32 B · version prefix 1 B on v0 only · each signature 64 B.

2 · Instructions

Per instruction: 1 B programIdIndex + compact-u16(numAccounts) + 1 B per account index + compact-u16(dataLen) + data bytes.

3 · Address table lookups (v0 only)

Per lookup: 32 B table key + compact-u16(w) + w + compact-u16(r) + r. Legacy txs cannot carry lookups.

    6 · compact-u16 — where the overrun hides

    Value rangePrefix bytesExample
    0 … 127112-byte transfer data → 1 + 12
    128 … 163832128-byte memo data → 2 + 128 (the +1 trap)
    16384 … 20971513practically unreachable in one tx

    Every vector (signatures, keys, ix count, ix accounts, ix data, lookup lists) carries such a prefix. Growing data 127→128 costs 2 bytes, not 1. serialize() then overruns its fixed-size buffer and throws instead of reporting the size — hence this calculator.

    7 · If you are over 1232

    • Split into two transactions (most reliable fix for Q23875-style failures).
    • Compress with ALT: move read-only accounts into address table lookups (v0) — each repeated 32 B key becomes a 1 B index.
    • Shrink data: drop memo/logs padding; prefer u8/u16 counts over strings; batch fewer ix per tx.
    • Recount prefixes: after edits re-check every compact-u16 boundary (127/128, counts of keys/ix).
